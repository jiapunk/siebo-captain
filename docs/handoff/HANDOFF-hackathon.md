# 🧊 賽博隊長 — 交接文件（hackathon vertical｜破冰優先）

> 版本 v1 ｜ 2026-09-18 ｜ 來源：Surrodate repo 拆分 ｜ 建議新專案代號 `siebo-captain`

## 0. 重新定位（與約會版的關鍵差異）

使用者的洞見：**黑客松最痛的不是組隊，是一開始的「破冰」——一群陌生人報名後互不認識，開場十分鐘沒人講話、群組裡全是「有人要一起嗎」的尬貼文。**

所以這個產品不是「組隊工具」，是**陌生人快速變熟的社交引擎**：

> **「你負責寫 Code，隊長負責去破冰。」**

| | 舊定位（單純組隊） | 新定位（破冰優先） |
|---|---|---|
| 核心問題 | 找不到隊友 | 不敢/不會跟陌生人開口 |
| 產品動作 | 配對 → 組隊 | **互盤 → 破冰卡 → 組隊 → 開工破冰** |
| 交付物 | 隊伍提案 | 隊伍提案 **＋「最該先聊的 3 個人」與開場話題** |
| 主辦方價值 | 組隊率 | 組隊率＋**參與者互動率**（活動體驗的直接指標） |

## 1. 使用者旅程（目標設計，含現況標記）

```
報名活動（Event code）
  ↓
建選手卡（6 題訪談）                       ✅ 已實作（hack domain pack）
  ↓
【開場前】隊長互盤（背景）                  ✅ 已實作（5 位候選平行、配對評分）
  ↓
【開場前】破冰雷達：最該先聊的 3 個人        ⬜ 要做的核心新功能
   └ 每人一張「破冰卡」：共同點、互補點、第一句話（點一下複製）
  ↓
【現場】同桌/活動破冰（QR 進桌、N 人互相的破冰題）  ⬜ P1
  ↓
隊伍提案（2-3 隊，附覆蓋率與風險）           ✅ 已實作（teamAssembler）
  ↓
加入 → 團隊群聊 → 隊友依角色認領工作         ✅ 已實作（teamBot 模擬隊友）
  ↓
【賽中】團隊章程生成（分工表、里程碑）       ⬜ P1
```

### 已實作功能（可直接沿用）
- 選手檔案：角色（前端/後端/全端/設計/PM/資料/AI）、技術棧、參賽目標、可投入時間、合作地雷
- 隊長互盤：**技能互補重於重疊**（同角色扣分、三角色覆蓋加分）
- 隊伍提案：N 對 N 聯盟形成（以兩兩分數為底＋角色覆蓋＋目標一致），2-3 隊，加入後自動收回其他提案
- 團隊群聊：SSE、typing、模擬隊友依角色認領（「簡報跟 Pitch 我來扛」「後端 API 我先開」）
- 分享權限：地雷欄位預設不對外，連對方 agent 都看不到

### 要做的核心新功能：破冰雷達 + 破冰卡（P0）

**破冰雷達**：互盤完成後，除了「隊伍提案」，每個人會得到「最該先聊的 3 個人」清單（依互補度與共同點排序）。

**破冰卡**（每個人選一張，可分享到 Discord/Threads）：
```
🧊 你的隊長幫你偵查到 小滿
├ 共同點：TypeScript、都全程投入
├ 互補點：你是全端、他是前端 → 你可以 cover 後端，他能讓畫面好看
├ 風險：目標不同（你想拿獎、他想學習）→ 先講清楚期待
└ 開場三句（點一下複製）：
   1.「我也是全程投入派。你前端做幾年了？我後端可以 fully cover。」
   2.「如果你的目標是學習，我建議我們 demo 走小而深，你覺得呢？」
   3.「先加個 Discord？我把架構圖丟給你，五分鐘就能對齊。」
```
- 技術實作：`llm.icebreakers` 已存在（目前用於配對成功後的約會場景）→ 換 hack 版 prompt（共同技能、互補點、目標落差轉成**破冰話題**而不是「適合交往的理由」）；資料不用新表，`MatchRun.report` 已有材料。

## 2. 系統架構（拆分後保留的部分）

### 頁面
| 頁面 | 說明 | 來源 |
|---|---|---|
| `/` | Landing（單一產品，無 domain 切換） | 改寫自現有 page.tsx |
| `/onboarding` | 選手訪談 | 沿用（移除 domain 切換） |
| `/profile` | 選手卡編輯＋分享權限 | 沿用 hack 分支 |
| `/agent` | 我的隊長：互盤 live 轉播、「產生隊伍提案」 | 沿用 |
| **`/people`** | **破冰雷達：最該先聊的人＋破冰卡** | 🆕 |
| `/teams` | 隊伍提案列表 | 沿用 |
| `/team/[id]` | 團隊群聊 | 沿用 |

### API
沿用：`users`(加 Event 後調整)、`session`、`me`、`profile`、`onboarding/*`、`matching/run`、`agent/runs*`、`teams/*`、`bus/user`
新增：`GET /api/people`（破冰雷達清單）、`POST /api/people/[id]/icebreakers`（生成/取得破冰卡，可快取進 MatchRun.report）
移除：`matches/*`、`chat/*`（約會用）

### 資料模型（調整後）
```prisma
User         { id, name, emoji, tagline, isBot, createdAt }          // 去掉 domain
AgentProfile { userId, status, interview Json, compiled Json, visibility Json }  // HackathonProfile
Event        { id, name, startsAt, code }                            // 🆕 活動/場次
EventMember  { eventId, userId, joinedAt }                           // 🆕 報名關係
MatchRun     { id, userAId, userBId, status, events Json, reportA Json, reportB Json, eventId }  // 加 eventId
Team         { id, eventId, status, score, report Json }             // 加 eventId
TeamMember   { teamId, userId, role, accepted }
TeamMessage  { teamId, senderId, content }
// 刪除：Match、Message
```
> 有了 `Event`，配對範圍從「全平台」變成「同一場活動」——這對黑客松是必要的（你只想跟同一場的人組隊），也讓示範資料可控（種一場假活動）。

## 4. LLM 與成本

- 與約會版相同：OpenCode Go `https://opencode.ai/zen/go/v1`、`deepseek-v4.1-flash`、UA `siebo-captain/1.0`、`x-opencode-session`
- 一次完整互盤：候選 5 人 × 6 呼叫 ≈ 30 次呼叫（真 LLM 約 2-5 分鐘，livestream 讓等待變成看點）
- 破冰卡：可「懶生成」——點開某人時才生成並快取（存在 MatchRun.report 或新表）
- mock 模式必保留：E2E 零成本＋活動現場沒網路時的離線展示

## 6. Demo 腳本（現場用）

**90 秒版**
1. 「黑客松最痛的不是寫 Code，是開場沒人講話——我們讓每個人的隊長先去破冰。」
2. 建選手卡（或選 Demo阿飛）→「隊長出發」→ 指著 live 逐字稿：「這些是 agent 之間的互相盤點，本人問會尬，agent 問剛好。」
3. 破冰雷達：「你打開就有一份『最該先聊的 3 個人』，每個人附三句可以直接複製的開場白。」
4. 「產生隊伍提案」→ 三隊 → 加入 → 群聊，PM 隊友第一句就認領簡報。

**加長版**：兩位真人在兩個瀏覽器各選一個隊長 → 互盤 → 互相收到破冰卡 → 直接照著卡片念第一句 → 全場笑。

## 7. 路線圖

### P0（第一版可上線）
- Event 模型＋活動 code 加入
- 破冰雷達 + 破冰卡（本文件第 1 節）
- 真 Auth（活動報名資料匯入 or OAuth）
- 內容安全：技能誇大防範（見風險）、檢舉封鎖
- 部署（Vercel + Postgres；SSE 限制確認）

### P1（體驗深化）
- 現場模式：QR 進桌、同桌 4-6 人的輪轉破冰題（agent 依在場者檔案即時生成）
- 團隊章程生成：分工表、milestone、demo 腳本骨架（給 teamBot 更多資料）
- 與 Discord/Line 通知整合（開場提醒、破冰卡直送）
- 主辦方後台 v0：報名→組隊率、互動指標匯出

### P2（商業化）
- 主辦方付費方案（每場活動計價）：組隊率、破冰完成率、贊助商曝光
- 活動後的團隊追蹤（專案繼續做 → 社群留存）
- 開放 Agent Card：讓主辦方系統或 Discord bot 直接呼叫隊長 API

## 8. 風險與對策

| 風險 | 對策 |
|---|---|
| 技能誇大（agent 都說自己會） | P0 就要有可驗證憑證：GitHub 連結驗證、作品集、主辦方審核欄位；報告標示「未驗證」 |
| 個資與主辦方資料 | 活動 code＋參賽者同意書；不導入名單，一律本人授權 |
| 現場網路不穩 | mock 模式＋預先互盤（活動前一天跑完，現場只讀結果） |
| 破冰題目冒犯 | prompt 護欄：不問年齡/性別/公司機密；提供「換一組」按鈕 |
| 組隊馬太效應（強者被搶） | 提案演算法已用覆蓋率平衡；可加「新手保護」權重（P1） |

## 9. 待決問題（需要產品負責人拍板）

1. **活動綁定 vs 開放平台**：一定要有 Event 才能用，還是開放配對（像約會版）？主辦方價值在「綁定」，社群價值在「開放」。
2. **首發合作對象**：TRAE 黑客松？大學社團？企業內部黑客松（如金融業）？名單決定 P0 功能的優先級。
3. **收費模式**：主辦方付費 vs 參賽者免費增值（履歷/作品曝光）？
4. **與現有工具關係**：Discord 是競爭還是載體？（破冰卡直接送到 Discord bot 可能是最低摩擦的入口）
5. **前身關係**：`siebo-captain` 要不要保留「約會模式」程式碼作為未來聯誼活動的擴充？建議：不保留，保持單一職責。
